# Addressed memory replay

The opt-in memory runtime executes finite addressed reads, posted writes,
acknowledged writes, local L1 accesses and explicit fences. Packets traverse the
shared torus transport; source reads and destination writes consume bounded
shared memory service. This is a scheduling model without tensor/byte values,
firmware execution or measured silicon timing accuracy.

## Run the examples

From the repository root:

```sh
.venv/bin/python -m simulator_detailed.replay_memory --replay simulator_detailed/configs/memory_replays/generic_ordered.json
.venv/bin/python -m simulator_detailed.replay_memory --replay simulator_detailed/configs/memory_replays/wormhole_ordered.json
.venv/bin/python -m simulator_detailed.replay_memory --replay simulator_detailed/configs/memory_replays/generic_incomplete.json
```

Each invocation prints one JSON result. `--output /path/to/result.json` writes the
same bytes, including a final newline. Exit codes are **0 complete**, **1 invalid
input/execution error**, **2 valid but incomplete**. Input admission and result
serialization precede output replacement; invalid replay inputs preserve an
existing output. Traces are intentionally detailed: the Wormhole example exports
63,099 transport events. Redirect stdout or use `--output` when inspecting it
outside an interactive terminal. No result files are generated by default.

| Example | Coverage | Result |
| --- | --- | --- |
| `generic_ordered.json` | Synthetic 3×3 dual torus; F=16, D=8, H=2, 24-byte segments, 4-byte address alignment; 125 MHz NoC / 250 MHz memory / 500 MHz ACI | Complete at 387 ACI cycles |
| `generic_incomplete.json` | Same operations, horizon 80; reports outstanding dependencies, descriptors, packets, service and access owners | Incomplete at 80 ACI cycles |
| `wormhole_ordered.json` | Profile-derived 240 routers / 480 links / 86 resources; both fabrics; `tile_0_0_noc0` and `tile_0_1_noc1` share `dram0`; 8,193-byte write split into 8,192+1 | Complete at 1,382 ACI cycles |

The examples produce local data, issue an acknowledged write, independently issue
a posted write, read back a produced range through the other fabric, fence the
read/acknowledged write, and consume the readback locally. A disjoint local read
competes for the same L1 service. All endpoint staging/queue, responder and local
client limits are one; segment issue capacity is two. Wormhole memory and NoC
rates/latencies are explicit example assumptions. The checked-in worker mask is
an illustrative profile assumption, not a detected card configuration.

## File and Python contracts

An executable file is `MemoryExecutionReplay` in `memory_execution.py`: exact
`kind=memory_replay`, strict integer `schema_version=1`,
`model_revision=addressed_memory_v1`, all `MemoryReplay` admission fields and a
required `runtime` object. Unknown fields/modes, nonfinite values and missing
runtime settings fail validation. The base Python `MemoryReplay` remains useful
for pure admission/packet compilation; it does not contain runtime settings.

- `source` is tagged `canonical_graph`/`hardware_profile`. Its path is relative to
  the replay file. Canonical graphs require complete explicit connectivity and
  resolved enabled attachment permissions. Optional endpoint port declarations
  must agree with that graph.
- Profile sources require explicit `routing` availability/policy bindings and
  endpoint `inject_port`/`eject_port` declarations for the directions used. The
  shared torus binder resolves ports and links from raw coordinates. Unselected
  endpoints cannot carry replay traffic; harvested workers cannot inject.
  Inspection alone does not enable execution.
- `resources` covers every canonical graph resource exactly once. Capacity comes
  from the graph/profile, with optional reductions. An alias never adds capacity
  or a service server. `endpoints`, `buffers` and `operations` name these resources
  and resource-relative extents explicitly.
- `packet` sets physical bytes F, useful data capacity D, header flits H, maximum
  software segment payload P and address alignment A. Buffer base/size and
  operation starts obey the configured aligned subset; useful lengths may end
  partway through a flit/granule.
- Each resource supplies `aggregate_shared_rw_v1`, native clock, granule/chunk
  sizes, combined read/write bytes per native cycle, fixed latency and waiting
  queue capacity. Queue capacity excludes the single active service slot.
- `runtime.transport` sets every fabric's local/network link clocks, widths,
  serialization/propagation/credit timing, lane/staging bounds and router service,
  with optional directed slowdown overrides. Endpoint capacities must agree with
  the admission fields. `runtime` also supplies responder/local-client bounds and
  request/response/local control costs. Issue cost/segment bounds are admission
  fields. Explicit evidence distinguishes assumptions from source-backed facts.

`replay_memory.load_plan(path)` performs pure admission, routing, ordering and
resource checks before constructing a SimPy environment. `run_replay(path)` runs
that plan. Existing Python composition remains available:
`MemoryPlan` → `MemoryExecutionPlan` → `MemoryRuntime`.
Revalidation checks the original profile and the admitted graph/configuration,
including protection against Python-side modification of a compiled plan.

## Execution and ordering

A read has a real header-only request, remote memory reads, header-plus-data
response and initiator-local memory writes. A posted write completes at final
local request handoff; its remote effects can still be pending. An acknowledged
write completes only after destination service and return of every segment's
header-only acknowledgement. All requests/responses share physical transport and
bounded staging. No operation has a private network or uncharged payload array.

A local L1 client uses the same capacity/readiness/service owner without generating
network packets. `source_version` selects initial data or an explicit producer.
`depends_on` waits for observable completion. `destination_ready_after` exposes
local resource effects only to eligible local consumers. Conflicting physical
ranges require sufficient explicit ordering, including accesses through aliases;
disjoint operations and concurrent reads can overlap.

Fences name a frozen set of earlier operations from the same canonical initiator,
optionally restricted by fabrics. `local_handoff` waits for request handoff;
`remote_completion` waits for read/acknowledged-write completion and rejects
posted writes. Later operations wait on fences only through explicit dependencies.
There is no implicit global program order or cross-fabric sequential consistency.

Replay success additionally requires remote effects, service queues, accesses,
descriptors, packets, staging and delayed credits to drain. Buffers stay reserved
through the finite replay and are released during successful teardown. An
incomplete result retains current ownership and never fabricates completion or
releases pending capacity. `memory_resources` is the pre-teardown snapshot;
`released_resources` is the post-teardown snapshot, present only after success.
This finite reservation policy is not a dynamic circular-buffer allocator.

## Accounting and reproducibility

All runtime timestamps are ACI cycles. Each completed chunk also exports native
clock/cycles and ACI conversion. A chunk of useful size B at address a with granule
G costs `ceil(((a mod G) + B) / G) × G` serviced bytes, then
`native_cycles = fixed_latency_cycles + serviced_bytes / bytes_per_cycle` and
`ACI_cycles = native_cycles × aci_clock_hz / native_clock_hz`.
The aggregate policy does not separately model narrow-write read-modify-write.

| Field | Meaning |
| --- | --- |
| `logical_bytes` | Planned operation useful bytes, including local accesses; fences are zero. A network read/write counts its logical range once. |
| `wire_packets[].definition` | Every planned packet's operation/segment/purpose, layout and exact route; includes packets not yet issued. |
| `wire_packets[].planned` | Useful, header, padding and physical packet bytes; `H×F + ceil(B/D)×F`. Headers carry no useful payload. Padding includes unused data-flit capacity. |
| `wire_packets[].injected` | Same decomposition for flits actually launched on the injection channel; incomplete packets contribute only their launched prefix. |
| `accounting.planned_network_logical_bytes` / `planned_local_logical_bytes` | Separate planned network/local useful work. Only the former appears as useful wire data. |
| `accounting.planned_wire` / `injected_wire` | Summed per-packet planned/actual byte decompositions. |
| `packet_bytes` | Actual injected physical bytes, once per flit; equals `injected_wire.packet_bytes`. |
| `channel_bytes` / `accounting.launched_channel_bytes` | Actual physical `link_launch` bytes over injection, network and ejection channels. |
| `accounting.planned_channel_bytes` | Each full packet's physical bytes multiplied by its route channel count. |
| `memory_service_bytes` | Rounded bytes of **completed** memory chunks. Active/queued work contributes pending identities, not completed byte totals. |
| `accounting.completed_{read,write}_{useful,service}_bytes` | Separate useful and rounded completed work by memory direction, including local clients. |

`transport.trace`, endpoint/resource snapshots, `lifecycle`, `descriptor_trace`,
`ownership_trace`, `service_trace`, `chunks` and `pending` allow separate audits.
Response receipt is actual final response-flit arrival, before local memory
service; it is distinct from the transport kernel's post-consumption receipt.
Service records never charge packet headers as memory data. Operation and segment
records preserve partial-order lifecycle facts and posted completion semantics.

`plan.source_json` preserves the normalized admitted graph and, for profiles, the
complete original normalized profile in `origin.document_json` with its digest.
`plan.configuration_json` preserves admission settings and evidence. Source,
configuration and memory-plan hashes are exported separately;
`execution_plan_sha256` additionally covers `settings` and execution policy.
Source paths do not affect identity, but their original spelling remains in the
configuration JSON. Changing runtime settings changes execution identity.
These are content identifiers, not code identities, hardware measurements or
accuracy certificates. The delivery report records code and example identities.

## Evidence and limits

Packet evidence is pinned to
[tt-isa-documentation revision acaf010519f4fdd323df5077e45b8695f70e4279](https://github.com/tenstorrent/tt-isa-documentation/tree/acaf010519f4fdd323df5077e45b8695f70e4279/WormholeB0).
The example embeds the NoC overview, memory-map and alignment URLs, immutable
revision and SHA-256 values. Full packet/order/L1/DRAM source identities and the
limits of each claim are recorded in the [change design](../../openspec/changes/wormhole-memory-transactions/design.md).
Profile/coordinate evidence is inherited without discarding its provenance.

These sources support structure and normal transaction semantics. Queue bounds,
issue/control cost, clocks, arbitration, aggregate bandwidth, chunk timing and
readiness scheduling remain configurable model assumptions. Tests independently
check byte arithmetic, service timelines, both-fabric/alias/local contention,
conservation, finite drain, errors and legacy compatibility. No matched hardware
measurement, external simulator comparison or calibration has been performed.

Unsupported scope includes MMIO/registers/counters, exact NIU ordering/automatic
splitting, linked packets, byte masks/immediate writes, atomics, multicast,
semaphores/scalar execution, L1 bank/port timing, DRAM banks/rows/channels/refresh,
byte/tensor values, dynamic circular buffers, DFG/compute integration, host/firmware
and multi-chip traffic. Within this initial API, one enabled target attachment is
selected per backing resource per fabric; the example uses different physical
aliases across the two fabrics. Arbitrary per-operation alias selection on one
fabric is not exposed.

`hardware-profile-3` advertises the **opt-in memory replay** scope. The general
profile workload gate remains closed. Legacy DMA/scratchpad adapters are explicit
Python APIs; legacy DMA does not acquire addressed-memory visibility semantics,
and existing DFG execution has not migrated. Detector/encoder inputs retain their
legacy contracts and reject memory replay/results. Optional Torch/PyG forward and
checkpoint behavior is not validated where those dependencies are unavailable.
